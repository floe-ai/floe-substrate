### Original 18-step scenario

Restored from the operator-provided handoff, floe-end-state-product-and-substrate-handoff.md, dated 2026-09-03. Source SHA-256: 4f3731c41810d78d59382f31f7b0066d1f3eb495a05faf7655282f725673d6cf.
The original numbered requirements follow verbatim. Each step is Pending until its evidence is recorded; the smaller operator attempts above do not replace this scenario.

The following scenario is not the product boundary. It is a conformance journey that exercises the whole end state.

1. The operator asks in chat for a system that turns Markdown campaign cards into tested, approved, published gallery websites using an external image service.
2. The coordinating Actor creates a Scope, clarifies success and publishing authority, searches existing Actors, capabilities, connectors, and templates, then forms the required team.
3. If the image or publishing connector is missing, a Builder Actor creates an Extension, tests it in isolation, declares network, credential and side-effect permissions, and requests installation approval. The credential broker binds a SecretRef under a scoped CapabilityGrant without revealing the secret to the model.
4. The coordinating Actor drafts a composition with Event-source, Actor, Context, Command/capability and external-action placements; typed Ports; explicit Edges; activation and Context policies; instructions; joins; human decision outcomes; and budgets. Floe validates and simulates it, shows the operator material risks and permissions, then publishes a revision.
5. The Scope accepts a watched folder, a signed webhook and a scheduled reconciliation sweep as typed sources. Duplicate webhook delivery and a restart across the schedule boundary produce no duplicate logical work.
6. A Markdown card is registered as a stable Artefact with an immutable version. Its frontmatter may carry the stable ID and authored metadata, its body contains the brief, and namespaced sections may hold extension projections. The mutable path is not identity.
7. A planning Actor produces a generation-manifest version and composite concept image derived from that exact card version.
8. A deterministic split capability emits N separately addressable child image Artefacts using stable manifest member keys. Fan-out produces independent Deliveries and NodeExecutions with their own Contexts. Duplicate ingress or retry produces no logical duplicates.
9. Each image can succeed, fail, wait, or be redone independently. The operator can select one token, inspect its exact version and lineage, enter its Context, correct an instruction, and redo only that branch.
10. When an image-processing Actor is deliberately asked to publish externally, it refuses the out-of-charter action and delegates to the authorised publishing Actor; if that Actor is unavailable, the obligation appears visibly unowned.
11. A keyed gather waits for the exact manifest membership, accepts out-of-order children, exposes missing or failed members, and emits an asset-collection ArtefactVersion containing exact child-version references.
12. A website-builder Actor consumes the card lineage and collection, producing a WebsiteTree ArtefactVersion backed by a Git tree, immutable folder manifest, or equivalent content-addressed snapshot. Member files remain addressable.
13. A tester consumes that exact WebsiteTree version and emits a TestReport proving which version, environment and checks were used.
14. A human-backed verifier receives the site, report, summary, evidence and Context in the attention inbox. Their signed decision Event references exact reviewed versions and leaves through `approved`, `changes_requested`, or `rejected` Ports. A standalone Decision Artefact is created only if a durable review document exists.
15. `changes_requested` follows explicit Edges to the relevant placement and creates immutable redo lineage. `approved` authorises the publishing connector for that exact WebsiteTree and target. Changed content invalidates the approval.
16. An Actor installs a campaign dashboard lens contributed by the Extension. It displays canonical Scope, Artefact, approval and publishing state and can be removed without data loss.
17. The final Scope workspace shows the authored design, live and historical runs, Actor organisation, all Artefacts and branches, Context conversations, decisions, external actions, costs, failures and recovery, with no route inferred from Context membership.
18. The same core behaviour survives process restart, runtime-provider replacement, mobile approval, and execution through public APIs without relying on hidden UI state.
